# Catálogo operativo de componentes Lemoon

Antes de crear o modificar UI, localizar la familia aquí, abrir su receta y leer el contrato en el archivo canónico. Reutilizar el snippet con sus dependencias; para una composición de sección, conservar su dueño nativo. [DESIGN.md](../../DESIGN.md) mantiene las decisiones visuales; [marca](../design/brand-guidelines.md) y [guía de selección](../design/component-library.md) completan el contexto.

## Elegir una receta

| Necesidad | Receta | Piezas principales |
| --- | --- | --- |
| Guía, títulos y ayuda | [Guía y ayuda](recipes/guide-help.md) | heading + action; shell local |
| Contacto nativo, campos y respuesta | [Formulario](recipes/contact-form.md) | field + message + action |
| Preguntas agrupadas y richtext | [FAQ](recipes/faq-group.md) | faq-item + heading; grupos locales |
| Ordenación y resultados | [Búsqueda](recipes/search-sort.md) | select + facets; formulario dueño |
| Catálogo comercial y tarjeta | [Grid de productos](recipes/product-card-grid.md) | card-product, price, swatch; contratos existentes |
| Demostraciones y estados | [Galería](recipes/catalogue-states.md) | seis snippets UI y límites legacy |

## Contratos compartidos

Las seis extracciones nuevas viven en `snippets/lemoon-ui-*.liquid`; su LiquidDoc define los parámetros, opcionales y defaults. Los snippets existentes conservan sus nombres y APIs. Los ejemplos de estas recetas son llamadas a esas fuentes, no otra implementación de HTML/CSS.

Enviar strings/atributos sin preescapar: los snippets UI escapan una vez en la salida. Los slots `_html` reciben solamente capturas de plantilla confiable; escapar cada dato externo dentro de la captura. `editor_attributes` recibe solamente `block.shopify_attributes`. El consumidor genera IDs únicos con sección/formulario/bloque y conserva formulario, rutas, locales, disponibilidad y lógica comercial. Mantener la diferencia entre booleano `false`, atributo omitido y string: no usar defaults que conviertan `false` en otro valor.

Los snippets UI usan los tokens → `base.css` → `lemoon-components.css` del layout y el CSS local de cada consumidor. No cargan una hoja por render. Conservar clases locales; `style_family: 'local'` de action evita añadir `.button`. La corrección de borde/foco de DESIGN se aplica a controles migrados; no declara resuelta la deuda de campos legacy.

## Familias y disponibilidad

**Reutilizable** identifica código canónico renderizable y sólo el alcance descrito, no un wrapper para toda la familia. **Composición de sección** conserva schema, objetos Shopify y controlador en su superficie. **Extracción pendiente** tiene implementación local, pero carece de átomo universal aprobado. Cada fila enlaza el contrato detallado del [inventario](../design/component-inventory.md) y una receta de integración; esa receta no significa que la familia haya sido migrada por LEM-142.

## Segunda adopción acotada

[Newsletter footer](../../sections/footer.liquid) y [comentarios](../../sections/main-article.liquid) reutilizan field/action/message; [shell legal](../../sections/lemoon-legal-page.liquid) reutiliza heading/action en los cinco templates legales; [FAQ legacy](../../sections/lemoon-faq.liquid) reutiliza heading/faq-item en page.preguntas-frecuentes. Formularios, copy, CMS, routing, moderación y editor permanecen en cada sección. Contratos opcionales y límites en las recetas de [formularios](recipes/contact-form.md), [ayuda](recipes/guide-help.md) y [FAQ](recipes/faq-group.md). El contorno/foco aprobado se aplica a los controles adoptados con el CSS compartido existente.

## Integrar y comprobar

1. Leer LiquidDoc y el consumidor enlazado en la receta; verificar contexto nativo, CSS/JS y claves de locales antes del render.
2. Conservar estados que pertenezcan a la superficie: normal, hover, foco, selección, loading, error y disabled sólo donde tengan sentido. El dueño proporciona feedback y recuperación reales.
3. Revisar teclado, IDs, label/ayuda/error, contenido largo y responsive en la integración. Las pruebas de fixtures locales no acreditan procesamiento Shopify, asignación del editor, publicación ni aprobación visual.
4. Registrar incorporaciones, modificaciones o retiros en el inventario MD/JSON y cobertura **en el mismo PR**, siguiendo su [regla de mantenimiento](../design/component-inventory.md#mantenimiento-del-inventario). Si cambia una API, actualizar también su receta y pruebas consumidoras. La ausencia de render estático no demuestra desuso.

## Evidencia y fuentes

Los consumidores ejecutables y sus pruebas se enlazan por receta. Los contratos reales prevalecen sobre ejemplos históricos; la cobertura actual está en [component-inventory.json](../design/component-inventory.json). La galería conserva elementos independientes legacy/demo; sólo los renders identificados ejercitan snippets canónicos. No equivale a un storefront aprobado ni a una certificación WCAG.
