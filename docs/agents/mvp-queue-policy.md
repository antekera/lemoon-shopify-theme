# Bounded MVP delivery queue

Use this policy only when the requester authorizes an MVP queue run. It adds ticket selection to `.codex/agents/linear-delivery-coordinator.toml`; that definition remains authoritative for implementation, review, PR handling, and Linear status ownership. This document is a coordinator procedure, not a scheduler or a running service.

## Scope and limits

- Project: Lemoon, UUID `75a7f897-f555-4606-a900-7e68ddb3995d`; team LEM. Verify those identities live before selection. Strategy: LEM-56.
- Repositories: `antekera/lemoon-shopify-theme` and `antekera/lemoon-next-backoffice`. Resolve actual checkouts and Orca workspace selectors; never infer them from a directory name alone.
- Pilot: select up to **three distinct execution tickets** for one batch. Freeze that list in the checkpoint before dispatch. Do not expand it, silently substitute a fourth ticket, or start another batch. If fewer than three are ready, process the ready subset and explain the shortfall.
- At most **two tickets** may be active concurrently. A ticket stays active through implementation, testing, and independent technical review. Waiting for human review releases its execution slot; the frozen batch limit still applies. Separately obey the runtime's total worker limit, counting reviewers/testers and the coordinator where applicable. File overlap or insufficient capacity reduces concurrency; it never increases it.
- Default delivery boundary: reviewed PRs ready for human review, with current required checks passing. Commit, push, open/update the selected tickets' PRs, and reply to their reviews within the authorized run. Move each ready ticket to Review and wait for the designated human reviewer's explicit approval of that ticket/revision; approval authorizes required merges and completion under AGENTS.md. A queue instruction never substitutes for individual review. Shopify publication, deployment, app installation, scope expansion, real payments/customer messages, and production writes remain separate authorizations under repository rules.
- Creating or editing this policy starts no Run, worker, ticket, automation, or background monitor.

## Determine the eligible queue

1. Read the complete live project issue list, following pagination. Load milestones, labels, actual state IDs, LEM-56, and relevant issue relations/comments. An incomplete list cannot support a claim that the whole queue was audited. If discovery is partial, checkpoint the limitation and complete discovery before selecting.
2. Reconcile evidence in this order: current explicit instructions from the requester; confirmed decisions in ticket comments/LEM-56; current ticket acceptance/dependencies; older project/milestone summaries. The latter still describe a frame-only MVP in places. LEM-23, LEM-24, LEM-140, LEM-138, and LEM-139 remain MVP-critical; do not defer them because an old summary says prescription commerce is later. Preserve genuinely future scope such as virtual try-on and advanced WhatsApp/AI work. Report an unresolved material conflict rather than inventing a decision.
3. Include explicit MVP work and its necessary foundational prerequisites. Inspect M0–M6 candidates, and later milestones only for explicit current MVP requirements. Milestone membership alone is neither authorization for future work nor proof that every earlier milestone must be Done. Exclude archived, canceled, duplicate, explicitly post-MVP, and administrative tracking/launch umbrella tickets as execution units.
4. Default intake selects unstarted Todo tickets using the team's live state definitions. Exclude tickets in In Review, Done, or a state a human maintainer established for manual review. Resume In Progress work only when this Run already owns it or the requester authorized its handoff; inspect ownership before any takeover. Inspect existing branches, worktrees, PRs, and acceptance evidence in both repositories. An open PR or dirty checkout can contain the missing feature already. Reuse scoped existing work when safe and authorized; preserve all unrelated product edits. Do not start another implementation over it or merge unrelated PRs to clear a blocker. Reopened tickets require investigation, not automatic dismissal because an old PR exists.
5. A candidate is ready only when it has a bounded deliverable, observable acceptance, a known repository/owner, available references/access, and sufficiently resolved business/design/integration decisions. Technical prerequisites need usable artifacts at known SHAs and applicable checks. Decisions requiring human approval remain blocked until the responsible owner provides it; no elapsed time supplies approval.
6. Distinguish technical readiness from Linear review state. A prerequisite may have usable, checked artifacts while awaiting human review. Record exact evidence and any explicit review gate; never change its status to manufacture readiness. A merged PR alone does not prove end-to-end behavior or a business/design decision. Unmerged dependency artifacts require an explicit compatible branch/contract plan and applicable authorization before dependent execution.
7. Document inferred missing dependencies and conflicts in the selection report/owning ticket. Do not restructure the backlog, create subtickets, consolidate/delete issues, change priorities/milestones, or remove dependencies as part of queue intake. If a ticket is too large, report the proposed split and choose another ready ticket before freezing the batch.

## Rank and freeze the batch

Rank ready candidates by: (1) prerequisite needed to unlock an explicit MVP-critical flow; (2) native Linear priority, treating unset priority after explicit priorities; (3) milestone order; (4) number of MVP tickets unblocked; (5) bounded size and independence; (6) issue identifier as deterministic tie-breaker. Do not select LEM-23 before its actual prerequisites merely because it is urgent.

LEM-141 (design guidance), LEM-55 (editorial guidance), LEM-93 (existing Shopify data audit), and LEM-140 (back-office contract/receipt) are intake starting points, not a fixed ticket assignment. Inspect their dependencies and existing artifacts before ranking. Guides must reuse approved decisions, not invent a new brand or make clinical/commercial promises.

Publish the selected IDs, reason, dependencies, role/file ownership, repository, and acceptance evidence plan in the run checkpoint and a concise progress update. Selection within this authorized queue does not need another ticket-by-ticket approval. Move each selected Todo ticket to In Progress only when its execution starts; preserve any state a human maintainer already set. Do not take over another worker's active ticket without verifying ownership and authorization.

## Execute with Orca

Resolve the Orca executable using the installed `orchestration` skill. Load its version-matched guide with `skills get orchestration`, plus the placement, coordinator-loop, messaging, or recovery reference at the corresponding action gate. Use real Orca Run/Task/Dispatch state for Orca-supervised execution; custom role names are instructions, not values for the provider's `--agent` flag. Pass the role definition in each Task spec and select an available provider without overriding the session's configured model/effort.

- Confirm Orca runtime identity, discover repository/workspace selectors, and bind one Run. On resume, use the existing Run instead of creating a second fleet.
- Create stage Tasks for the frozen tickets with real dependencies. Dispatch independent ready work within both concurrency limits. Each spec names target, concrete change, constraints, file ownership, and observable acceptance; include the role definition and repository rules. Editing workers share the codebase and must preserve others' work.
- Reuse exact safe workspaces. Create isolated ticket worktrees when branch/file conflicts or existing dirty product work make sharing unsafe; use Orca placement commands, verify the base SHA/remote, and do not copy unrelated uncommitted work. Two ticket branches sharing one mutable checkout are unsafe even with different files.
- Process every inbox Delivery before acknowledging it. Answer worker questions that existing decisions resolve; send remaining product/business questions to the responsible product owner, grouped by owning ticket. Continue independent selected work while waiting. Keep unresolved decisions as blockers in those tickets; do not invent answers or spawn extra tickets.
- Accept `worker_done` only for the expected active Dispatch and inspect its diff/evidence. A heartbeat, successful enqueue, timeout, or missing connection is not completion or proof of exit. Apply the installed recovery guide before retrying an attempt; never start duplicate editors on unknown liveness.
- Route corrections to the responsible implementation agent; use a different agent for independent review. Reviewer behavioral restraint is distinct from enforced session permissions, as defined in AGENTS.md. Follow the shared coordinator's validation and PR gates.
- After accepted settlement, explicitly reuse, retain when requested, or release each worker through Orca. Preserve changes if cleanup is refused; never force-remove a dirty worktree. Do not end with unaccounted active Dispatches or reclaimable terminals.

## Checkpoint and resume

The coordinator owns one non-secret checkpoint in the theme repository's Git common directory, under `lemoon-agency/runs/<run-id>.json`. Resolve that directory with Git instead of assuming `.git` is a folder in a linked worktree. Keep runtime checkpoints out of commits. Orca remains authoritative for live Dispatch ownership; the checkpoint is recovery context, not proof of liveness.

Record policy version/base SHA, project ID, frozen ticket IDs, selection/rejection reasons, delivery boundary/merge authorization, Run ID, Task/Dispatch IDs, stage, role/file ownership, worktree/branch/base/head SHAs, linked PRs, tested SHAs/results, acceptance/QA references, dependencies, questions, outcomes, the human reviewer's approval reference/scope/revision, actual Linear state IDs, and next action. Refresh after selection, dispatch, accepted settlement, a blocker, PR changes, and handoff. Link concise ticket-specific checkpoints in Linear without customer data, credentials, or full medical records.

Before resuming, read this checkpoint and the current Linear/PR/Orca state, inspect the actual checkout, and reconcile ownership and SHAs. Resume the same frozen batch. Do not reselect tickets already handed to Review. On an authorized continuation, resume approved tickets from their recorded approval and revision to finish required merges and completion, rather than reimplementing them.

## Delivery and stop conditions

An internal outcome is one of `ready_for_review`, `blocked`, `failed`, or `already_satisfied` with acceptance evidence. These are checkpoint outcomes, never new Linear statuses. `already_satisfied` counts only if the ticket's current acceptance was verified; a title match, screenshot, or merged PR alone is insufficient.

For `ready_for_review`, require final scoped implementation/content, relevant tests/QA, independent reviews, current PR checks, PR links, tested SHA, accessible preview/API or artifact evidence as applicable, and explicit environment gaps. A documentation deliverable may have a justified test/preview-not-applicable note. Missing required evidence, commercial decisions, or legal placeholders prevent this outcome. Add the handoff and move each ready ticket to the team's Review column. Apply AGENTS.md's lifecycle to every ticket, including `already_satisfied`: the designated human reviewer must explicitly approve its deliverable before required merges and completion. Record approval scope, confirm necessary merges and acceptance, then move it to Complete. Until then preserve the review handoff; unfinished or blocked implementation remains In Progress with its blocker. Preserve unrelated/unstarted ticket states.

Stop after the frozen batch has settled, or when its remaining work cannot proceed without a required human decision or external access. Settle/account for workers before ending. Report every selected ticket, outcome, evidence, PR/preview, blockers and grouped questions, plus the next recommended queue candidates. Never describe a partially blocked batch as successful, start a fourth execution ticket, mark an external goal complete with required work outstanding, or claim persistent execution after the active run ends. A later batch requires a new instruction or an explicitly authorized continuing goal.
