# Lighthouse CI

The PR gate measures the theme in a dedicated Shopify development store. The separate **Commercial Lighthouse audit** workflow measures the currently published commercial storefront, including its apps and tracking. Neither workflow blocks requests or repeats collections until a score passes.

Both use home, PDP and collection routes, three runs per route, and the same error thresholds: performance **0.60**, accessibility **0.80**. Known documentation/tooling-only PRs report Lighthouse as N/A through `scripts/ci_scope.py`; runtime and unknown paths require the gate. Main pushes and manual CI runs always audit. The commercial workflow is manual only; there is no new schedule. Run it before a release and review its results separately from the lab gate. Its reports describe the current published store, not the checked-out PR revision.

## Dedicated laboratory setup

Configure these repository values directly in GitHub; never put credentials in source or logs:

| Kind | Name | Value or purpose |
| --- | --- | --- |
| Variable | `LIGHTHOUSE_STORE` | `lemoon-lighthouse-lab.myshopify.com` |
| Variable | `LIGHTHOUSE_PRODUCT_HANDLE` | `lighthouse-frame` |
| Variable | `LIGHTHOUSE_COLLECTION_HANDLE` | `lighthouse-frames` |
| Secret | `LIGHTHOUSE_CLIENT_ID` | Dedicated lab Dev Dashboard app client ID |
| Secret | `LIGHTHOUSE_CLIENT_SECRET` | Dedicated lab app client secret |
| Secret | `LIGHTHOUSE_STORE_PASSWORD` | Lab storefront password |

The app needs `read_products` and `write_themes` (which includes theme reads). A human provisions the catalog; CI needs no product write scope. Verify app access to the lab before enabling the gate. The fixture also verifies the lab's immutable shop ID `102677381410`, its myshopify domain and CLP currency before creating a theme. Known commercial domains are rejected. Missing configuration fails clearly; there is no commercial credential fallback.

Keep the laboratory free of marketing apps/pixels and maintain its synthetic data and global preferences under operator control. This remains an operational prerequisite; theme code cannot enumerate or prove every externally configured integration. Existing `SHOPIFY_*` credentials remain separate and are never overwritten by this harness.

Import `scripts/lighthouse/fixtures/products.csv` in the lab only. Publish all 12 products to the Online Store, create the manual collection with the exact title/handle in `manifest.json`, include exactly those 12 products, and set product order to **Product title A–Z** (`ALPHA_ASC`). The CSV contains 24 SKUs, two Color variants per product, each priced at CLP 39,990. Attach each matching local PNG, exactly one image per product, and set its exact manifest alt text. Set these metafields on **every** product:

| Namespace/key | Type | Value |
| --- | --- | --- |
| `custom.lens_compatible` | boolean | `true` |
| `custom.lighthouse_fixture` | single line text | `lemoon-lighthouse-v1` |

The gate reads all products (requesting 13 to detect an extra entry), exact collection membership, titles, variants, options, prices, SKUs, metafields and media metadata. It also requires Online Store publication, fixed vendor/product type/tags, untracked inventory with CONTINUE selling policy, shipping enabled, tax disabled and no compare-at prices. The CSV supplies these values. Shopify filter configuration and global app/pixel settings still require operator review; CI does not claim to verify them. Local images retain source SHA256 hashes. Remote images are decoded with locked `pngjs` 7.0.0 and compared by exact RGBA pixel SHA256, width and height: Shopify may insert metadata or recompress a PNG without changing its pixels. Changed pixels fail; a gate never enrolls new image hashes automatically. `fixtures/generate.py` regenerates the original fixed PNGs, manifest and CSV offline; it makes no API calls.

Online Store publication is verified independently of storefront URLs: every product must be `ACTIVE` with a valid, nonfuture `publishedAt`. [Admin API 2026-10 documents `Product.publishedAt`](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/Product#field-Product.fields.publishedAt) as the Online Store publication timestamp, available with the existing `read_products` scope. Null, missing, invalid or future timestamps fail the fixture gate. [Shopify staff confirms](https://community.shopify.dev/t/onlinestoreurl-returns-null-even-when-filtering-with-published-status-online-store-channel/32775) that password protection can make `onlineStoreUrl` null regardless of publication, including on development stores. Neither a storefront URL nor a preview URL serves as publication proof. Password authentication and the HTTP 200, route and theme identity checks below remain required.

Each lab run stages only Shopify theme directories in a disposable copy, excludes any local `config/settings_data.json`, and writes the versioned `fixtures/settings.json` there. It preserves the actual homepage hero, enabled sections, card counts and theme assets, while mapping homepage section `collection` settings to `lighthouse-frames`. No commercial settings are pulled, and repository runtime templates/assets are not rewritten. Schema defaults supply unspecified settings; the theme's contracted font loading remains in the real layout.

## Reproducible harness and assertions

The harness uses the linux/amd64 Playwright 1.63.0 Noble image pinned by its platform digest in `scripts/lighthouse/Dockerfile`, including Chrome for Testing **153.0.8010.12** and the image's immutable Node/system libraries. `npm ci --ignore-scripts` installs exact direct and transitive versions from the harness lockfile: LHCI **0.13.0**, actual Lighthouse **11.4.0**, Shopify CLI **4.8.5**, Playwright **1.63.0**, Puppeteer **25.16.0**, and PNG decoder **7.0.0**. It downloads no browser at execution time. `versions.json` records actual Node/browser/package versions, platform, image digest, lock hash, source SHA and fixture manifest. Actual LHCI, Lighthouse, Shopify CLI and browser versions are checked before upload.

The dedicated authentication page disables JavaScript before its first navigation, enters the password through browser keystrokes and submits the native form; candidate theme scripts cannot intercept the password. It enables JavaScript again before readiness/scored pages. Before filling the password, the browser checks the page origin and resolved form action, and blocks all cross-origin requests from the first authentication navigation, including GET and native submitter `formaction`/`formmethod` overrides. The guard is removed before readiness/scored pages, where third-party resources run normally. It submits the real password form with the password passed as data, then visits every preview route and requires HTTP 200, the expected path/origin, no password form and the exact temporary theme ID. It retains authentication storage during collection. A custom Lighthouse gatherer runs after sensitive instrumentation on **each scored page**, and its identity audit rejects the wrong theme, role, password form or unexpected route. All nine LHRs must contain successful identity and HTTP status audits, expected final routes and Lighthouse 11.4.0 before assertions run.

LHCI 0.13.0 has a category-assertion defect: `median-run` selects a representative run for ordinary audit assertions, but category assertions still receive all runs and can choose the maximum score. `median.cjs` therefore selects the same pinned upstream representative run **once per route for both categories** into a private assertion directory, then invokes the actual LHCI assertion engine on those selected reports. Selection uses FCP/interactive proximity, never scores. Lighthouse 11 omits interactive; the upstream selector treats it as zero, leaving FCP to select the median. Missing/nonfinite FCP fails. All nine reports are preserved, and `versions.json` names the three selected report files. Thresholds and the declared `median-run` configuration remain unchanged.

## Harness trust boundary

The credentialed PR gate checks out the PR theme payload and a **separate immutable harness revision**: the PR base SHA, or the pushed main SHA. Manual runs require a 40-character `lighthouse_harness_sha` identifying an explicitly reviewed revision. The local composite action and Docker build context come from `.lighthouse-trusted`, rather than the PR-owned harness. Checkout credentials are not persisted for the credentialed gate. Theme source is mounted read-only, and staging rejects symlinks before uploading. Version evidence distinguishes the theme SHA from the reviewed harness SHA.

Bootstrap is deliberately fail-closed: the old base commit has no new harness, so a runtime PR cannot execute this unreviewed harness with credentials before approval. Run the secret-free **Lighthouse Harness Validation** job first; it runs on draft PRs, builds the pinned Linux image, executes actual LHCI/unit regressions, then collects nine scored synthetic localhost pages using real Chromium, password authentication and the identity gatherer. After review, a manual workflow can explicitly select the approved harness commit. No passing lab result is manufactured during bootstrap.

This is not full isolation from repository writers: a same-repository writer who can edit workflows or select a manual SHA may change those instructions. Branch protection, human review and GitHub's secret/environment policy remain trust prerequisites. Browser-rendered PR theme JavaScript is also untrusted; the lab storefront password grants only access to synthetic catalog data and must not be reused elsewhere. The Admin token stays in the runner/CLI, not the browser. This task adds no claim of a permission-isolated reviewer or credential sandbox.

## Cleanup and evidence

Before any upload, the runner persists an ownership record containing the lab domain and a random unique theme name. It creates a new **unpublished** theme, never a reused development theme. Once confirmed, it also records the numeric ID. Cleanup lists themes, checks exact name/ID and unpublished role, deletes only that ID and lists again to confirm absence. This also finds a partially uploaded theme when the push fails before returning JSON. Renamed, published, mismatched or ambiguous targets fail cleanup rather than authorize another deletion.

The runner attempts cleanup and report export after upload, collection and assertion failures, and handles SIGTERM/SIGINT. The composite action has an `always()` cleanup step with the durable ownership record as a second attempt. Cleanup failure fails the job and is reflected in the overall status artifact. An abrupt runner loss or hard kill can defeat both mechanisms; use the saved exact ownership record in the runner state or run logs/operator inventory to reconcile that interrupted run. Never bulk-delete other themes or substitute `--development` deletion.

GitHub artifacts have a 14-day retention period and use explicit file paths only:

- `lhr-*.json`: minimized, sanitized LHR JSON retaining category scores, audit references, numerical audit metrics, timestamps and final/requested URLs with query/fragment/userinfo removed.
- `assertion-results.json`: allowlisted assertion fields, including passing results and selected-run values.
- `versions.json`, `status.json`, `cleanup.json`: environment/selection evidence, non-secret exact cleanup ownership (domain/name/ID), and combined audit/cleanup status. Catalog, shop identity and GraphQL failures include an allowlisted `status.json` diagnostic with the failing field, manifest product handle where applicable, and bounded expected/actual values, or up to five GraphQL error messages and HTTP status. Known credentials and URL query/userinfo are removed before values are truncated; raw responses, headers and GraphQL extensions are excluded. The diagnostic does not relax fixture validation or prove a performance result.

Raw HTML, DOM, network details, headers, cookies, arbitrary JSON, private configs/auth files and raw command logs are excluded. Known credentials are redacted in plain, JSON/form/URL-encoded and base64 forms, including object keys. LHRs are intentionally minimized; they are not full interactive HTML reports. The harness performs no temporary public-storage upload and creates no GitHub/LHCI check using a separate token.

The commercial workflow uses the existing `SHOPIFY_STORE` and `SHOPIFY_STORE_PASSWORD`, plus explicit route handles and the public `SHOPIFY_STOREFRONT_ORIGIN=https://lemoon.cl` in its YAML. The store secret remains the myshopify identity; authentication, readiness and scored routes all use the explicit canonical storefront origin. Commercial configuration accepts only the exact trusted HTTPS origin `https://lemoon.cl`, with no userinfo, port, path, query or fragment and no fallback to the myshopify host. Lab origin construction remains unchanged. It needs no Admin access token. It visits published URLs without preview query overrides, requires `Shopify.theme.role === 'main'` and stable theme identity during readiness, and runs the same scored-page identity audit. It neither stages fixture settings nor creates/deletes themes. It preserves actual apps, pixels and production configuration. Unexpected market/domain redirects still fail origin/route validation; the configured canonical origin avoids the known myshopify-to-lemoon.cl redirect without bypassing redirect checks or filtering measured requests.

## Validation and acceptance

The hosted credential-free validation job is the Linux container check; its synthetic pages prove harness wiring only. Run `npm ci --prefix scripts/lighthouse --ignore-scripts`, `npm test --prefix scripts/lighthouse`, and the repository Python CI-scope/workflow tests. The harness tests exercise password data handling, readiness, artifact allowlisting/encoding, cleanup failures, fixture drift, the actual pinned Lighthouse config and actual LHCI baseline/regression assertions. These local tests are not a Shopify storefront run.

Before merging/activating this configuration, complete app/secret setup, verify the live fixture, run the pinned container against the lab, confirm exact cleanup and retained sanitized artifacts on success and forced failure, and compare repeated executions of the **same SHA and fixture**. Demonstrate a deliberate storefront regression fails the unchanged gate. These are live acceptance requirements; passing local synthetic assertion tests alone does not prove reproducibility, score stability or real theme regression detection. Keep the current gate unchanged on main until this dedicated-lab replacement is ready.
